## 诊断：刷新变慢 + 「仓位栏目消失两秒后出现」（00:55，**不是性能问题**）
- 实测（Temp/_perf_refresh.py 正常网 + Temp/_perf_slow.py 三档网速模拟，线上真实站点）：
  **三档网络下长任务(>50ms)都是 0 条** → 主线程几乎空闲，不是 CPU/渲染消耗。
- 真因 ①：**仓位栏目是 JS 动态插入的，而它前面的 `run-status.js` 是阻塞外链**。
  时间线：持仓板块(静态 HTML) 389ms 出现 → run-status.js 下载完(正常 304ms / 弱网 1085ms)
  → 内联 cost_panel.js 才执行并插入 #costManage。缺口：正常 349ms、慢网 407ms、**弱网 1662ms**
  —— 正好是用户说的"消失两秒后出现"。
- 真因 ②：刷新时一堆 no-cache 串行请求：status.json、api.github.com contents×2、
  raw.githubusercontent×3（data/position-costs + main/settings + main/holdings）。
  **最贵的是 run-status.js 的 publicTask 会整份重拉 index.html**（618KB / 传输 140KB，
  弱网 3230ms）—— 只为取 `script#snapshotData` 校验"Pages 是否已发布"（run-status.js:641）。
- 候选优化（未做）：A run-status.js 加 `defer`（或内联）→ 缺口归零（面板随 HTML 解析完即插入）；
  B index.html 校验改成读一个小体积 `snapshot-meta.json`（build 时产出，只含 run_id/sha/target），
  或用 Range 只取前 ~200KB（snapshotData 在 110KB 处），省掉整份 618KB 重拉；
  C 云端 position-costs 拉取延后到 requestIdleCallback；D api.github.com 两个 contents 请求按需发。

## 回答 iPad + 刷新卡顿的真正原因（01:00–01:30，改动未上线）
- **iPad 实测**（Temp/_diag_ipad.py，本地产物 index.html）：744/768/810/820/834/1024/1180 全部落在

  与桌面 1440 **一模一样**。所以 iPad 已经是电脑版样式，不是手机版。
  「看起来矮」是物理尺寸差：iPad 768px 铺满约 153mm → 1 CSS px≈0.199mm，50px≈**10mm**；
  24 寸 1440 → 1px≈0.358mm，50px≈**18mm**（iPad 只有桌面的 56%）。手机档 57px≈10.4mm，与 iPad 相当。
  要"更接近电脑"只能给平板单独加高（50→56/60）+ 加字号，代价是每屏少看 1~2 个分组（**等用户定，未做**）。
  ⚠ iPad 若用**分屏/侧拉**（竖屏 1/2=384px、1/3=254px；横屏 1/2=507px）会掉进 ≤600 手机档。
- **刷新卡顿诊断修正（推翻上一版结论）**：上一版说"run-status.js 阻塞外链导致栏目晚出现"——**实测不成立**。
  Chrome 的 preload scanner 会提前并行下载它，A/B（old 同步 / new defer / new async）弱网下栏目出现时间
  **15440 / 15466 / 15466ms，几乎相同**，DCL 也一样。真因是：**仓位栏目由 HTML 末尾内联的 cost_panel.js

  缺口 6.9s ＝ HTML 后半段下载时间（线上压缩 143KB 对应约 1.6s，与用户说的"两秒"吻合）。
- **本次已做两处改动**：① run-status.js 外链改 **async**（不阻塞解析、也不推迟 DCL；用 async 不用 defer，
  因为 defer 会把 DOMContentLoaded 一起推迟，栏目该晚还是晚）—— 实测持平但理论更优、零风险；
  ② index.html 复核改**条件校验**：request 加 `revalidate` 选项（cache:'no-cache'），走 ETag/304，
  未变更时零 body（curl 实测 Pages 带 ETag、`If-None-Match` → **304 len 0**，bust 加查询串也仍 304）。
  冷缓存被原样抛回 304 时递归退回一次 no-store 全量，保证拿到的仍是线上真实内容。

## 追问「为什么之前没有这个现象」（02:00，考古 + 定量，改动仍只有上面的 async/304）
- **考古结论：不是最新版引入的**。产物里 `run-status.js` 外链与内联 cost_panel.js 的相对位置、
  偏移比例从 **10-23（810090a）起就没变过**：run-status 在 ~80% 处、cost_panel 在 ~82% 处，
  其余历史产物（10-24/26/27/30 各版）同样。cost_panel.js 一直是 IIFE 立即执行（无 DOMContentLoaded、
  无 await/fetch 阻塞），面板一直由 JS 插入。→ 没有"某次提交把它挪后/改成等网络"这种突变。
- **定量分解（新脚本）**：
  · 线上正常网（Temp/_perf_refresh.py）：HTML responseEnd **393ms**（传输 144KB gzip / 解码 705KB）
    → run-status.js start=396ms dur=**279ms**（几乎串行，preload scanner 没并行上，因为标签在 80% 处）
    → 静态「持仓」分组 439ms 出现，**#costManage 705ms** 出现。缺口 266ms ≈ run-status 那 279ms。
  · 同条件 A/B（Temp/_perf_gz_server.py 本地 gzip 服务 + _perf_why2.py，1200kbps/RTT300ms）：
    sync **1419ms** / async **1250ms** / 去掉 run-status **1257ms** → **同步阻塞只值 170ms**，
    HTML 下载本身占 ~1230ms（87%）。→ "两秒"的大头是 **HTML 传输**，run-status 只是尾巴。
- **「以前没感觉」的真因＝缓存**：线上 index.html 与 run-status.js 都是 `Cache-Control: max-age=600`
  + ETag + CDN `X-Cache: HIT`；带 If-None-Match 重载实测 **304 / 60ms / 0 字节** → 十分钟内的重开、
  「返回看板」几乎瞬时，栏目与页面同时出现。而页面「刷新」按钮（monitor_render.py:14 HARD_REFRESH_JS）
  走 `location.replace` 带 `_r=Date.now()` → **URL 变化 → 浏览器 disk cache miss + CDN 也 miss**，
  每次都是全量 144KB 回源，用户网络下≈2s。也就是说：只有"点刷新/超过 10 分钟首次打开"才会看到这个现象。

  → 现在 **140,588**（两天 +19KB / +15%，主要来自 cost_panel.js 内联 124KB 源码与数据行长）。
